Results summary

These figures use only valid cases with matching relationship traces. Each case has equal weight; this is not a workload-weighted overall speedup. Plans are prepared ahead of execution, and schema work still differs. The comparison uses serial local engines with the backend identified below; it is not a production throughput benchmark. This summary covers the complete run, independent of the filters below.

Read the comparison at its measured boundary. Classic uses concurrency 1 and chunk size 1. QP uses opt-in schema order, targeted recursion, base-first exclusion, exhaustive .all traversal and coalesced direct/wildcard reads; caveats are evaluated at the final boundary. No dispatch result cache, advisor, gRPC, or network dispatch. The source includes PR #3386 and the mixed-trait expiration fix.

Measurement & interpretation

Dots show medians; thick bands show the 25th–75th percentiles; thin whiskers show min–max across repeated sample means. These are variability bands, not confidence intervals or request-latency percentiles. Raw samples, iteration counts, and request details are available under each case.

Timing and allocation runs have no work recorder. Work metrics come from separate audit runs. Data loads are forward/reverse relationship query calls; rows are relationships consumed, not physical rows scanned. Logical bytes use the same JSON relationship encoding for both engines, including traits; they are not network or on-disk bytes. Schema accesses count reader acquisition and definition lookups, including cache hits. Schema datastore loads are counted below the cache; they represent actual schema reads. Older reports without that instrumentation show no load count.

Speed ratios appear only when relationship traces match. Even then, schema handling and implementation overhead differ and are measured explicitly. Other cases remain visible with their work differences. Setup/plan preparation costs are separate, one-off observations per dataset/profile, shared by all its cases.

The delay profile adds a requested 100 µs to each relationship query on both engines. Actual waits depend on OS timer granularity. Dataset sizes describe the loaded snapshot; fixture setup is outside execution timing.
